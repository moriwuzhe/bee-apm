# LT Monitor 轻量化 APM 改造计划 (单兵/小团队专属)

针对当前单人开发、小公司维护的现状，抛弃复杂的“流式计算”、“多级集群”等重型架构，聚焦于**高效率管理、直观可视化和极简部署**。

核心目标是将 `LT Monitor` 改造为一个带有“控制面 (Control Plane)”的 APM，使得 Agent 的分发、配置管理和版本升级全都在一个统一的 Web 后台完成，并直观展示服务链路拓扑。

## 第一阶段：Agent 的集中管理与心跳机制 (控制面基础)
目前 Agent 主要依靠本地的 `config.yml` 运行，缺乏集中调度。

**改造内容：**
1. **Agent 自动注册与心跳**：
   - Agent 启动时，向 APM Server 发送注册请求（包含应用名、IP、进程ID、Agent版本）。
   - Agent 定期（如每30秒）发送心跳，汇报存活状态和基础性能指标（CPU/内存使用率）。
2. **APM Server 应用管理**：
   - Server 端新增 `Application` 和 `Instance` 表/索引，记录当前在线的应用和实例。
3. **UI 可视化**：
   - 在 UI 增加【应用管理】菜单，展示所有在线应用、实例列表、Agent 版本及健康状态。

## 第二阶段：Agent 的统一配置与动态下发
不再让开发者登录每一台服务器去修改 `config.yml`，改为后台统一控制。

**改造内容：**
1. **统一配置中心 (Server 端)**：
   - Server 端增加全局配置和应用级配置（如采样率、黑白名单、慢SQL阈值、插件开关）。
2. **动态拉取 (Agent 端)**：
   - Agent 的心跳接口响应中，携带当前应用的最新配置版本号（Version/MD5）。
   - 当 Agent 发现配置有更新时，主动调用 Server 接口拉取最新配置，并热更新到内存中（通过反射或 `AtomicReference` 替换）。
3. **UI 可视化**：
   - 在 UI 增加【配置管理】菜单，支持按应用名下发配置并实时生效。

## 第三阶段：Agent 的自动下发与平滑升级
解决每次发布新版 Agent 需要手动替换 jar 包的痛点。

**改造内容：**
1. **安装包托管 (Server 端)**：
   - 将不同版本的 `lt-agent.jar` 统一上传到 APM Server 后台进行托管。
2. **一键安装脚本 (Shell/Powershell)**：
   - Server 提供类似 `curl -sSL http://apm-server/agent/install.sh | bash` 的脚本。
   - 脚本执行时要求传入 `App-Name`，自动下载最新 Agent 并生成启动脚本/参数。
3. **Agent 自动更新提示 (UI)**：
   - 在 UI 的【应用管理】列表中，对比实例当前的 Agent 版本和 Server 上的最新版本。
   - 提供“升级指南”或未来支持 Agent 接收升级指令后自动下载新 jar 包并提示“下次重启生效”。

## 第四阶段：服务依赖拓扑图谱 (Topology)
链路追踪最终需要通过拓扑图来展示全局架构和依赖瓶颈。

**改造内容：**
1. **依赖关系聚合 (Server 端)**：
   - APM Server 在接收 Trace 数据（Span）时，提取 `Caller -> Callee` 的关系。
   - 比如 `前端 -> OrderService -> UserCenter -> MySQL`。
   - 将这些聚合后的依赖关系（按分钟/小时聚合调用次数、平均延迟、错误率）存入 ES/MySQL 的 `topology` 索引/表中。
2. **图谱渲染 (UI 端)**：
   - 使用 G6、ECharts 等图形库，在 UI 渲染出带有方向的连线图。
   - 节点代表应用/数据库，连线代表调用关系。
   - 线条粗细/颜色可反映流量大小和错误状态（如标红表示错误率高）。

---
## 极简架构总结
- **Agent**：负责采集数据、发送心跳、拉取配置。
- **Server**：直接接收 HTTP 请求（暂时省去 Kafka），一边写 ES/MySQL 存 Trace，一边处理 Agent 的心跳和配置请求。
- **UI**：统一的控制台，看链路、看拓扑、管配置、管 Agent。
